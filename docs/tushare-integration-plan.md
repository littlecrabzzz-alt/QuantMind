**1.1 本地与远端怎样开发**

| 场景 | 源码与算力 | 数据和命令入口 |
|---|---|---|
| Mac 日常全栈开发 | 优先本机 CPU/内存与 Docker Desktop；后端仍挂载源码目录 | 数据在 `.local-dev/project`、`quantmind-dev_*` 独立卷；先 `local-dev.sh status`，未运行才 `start core` 或按需 `start full`，仅首次初始化才 `init` |
| Mac 实验性后端改动 | 在 Syncthing 共享主树之外的独立 worktree 编码、测试 | 临时夹具/固定副本、隔离 DB/Redis/输出，无生产凭据；不能把候选代码写进共享树来“只测本地” |
| Linux 云端开发 | `lzy-vm` 宿主可开发和研究；候选代码同样放独立 worktree | 先 `sudo -n python3 scripts/dual_node_check.py --node cloud`；测试用隔离目录，正式写入只走云端业务作业 |
| 正式部署 | 回到已验证的云端权威入口 `/root/code/QuantMind` | 只有进入部署阶段才经 `sudo -n bash scripts/dual-node.sh cloud-compose ...` 应用变更；文档修改/提交本身不触发重启 |
| 本地离线查询/研究 | 使用本机镜像、依赖和固定输入版本 | 读取完整 Tushare 副本；索引/实验结果写独立目录；云端断开不切换数据权威角色 |

开始操作先检查 `uname -s`、`uname -m`、`hostname`、`pwd -P`、Git 状态、`docker context show`，并核对目标容器、角色及挂载。Mac 的容器也报告 Linux；容器内不能执行宿主迁移或启停脚本。Mac 联网完整预检为无参数 `dual_node_check.py`；Linux 不运行该无参数版本，也不运行 local-dev.sh、launchctl 或 APFS 克隆命令。Mac 离线可继续已有沙盒和固定夹具测试，联网预检在恢复连接后执行。

已核对的 local-dev 实现有两项重要边界：

- `.local-dev/project` 隔离的是数据；Compose 的 `./backend:/app/backend` 仍挂载主源码，主树变化会经 Syncthing 去云端。默认本地开发并不代表代码不会影响远端延迟导入，因此本次 Tushare 后端候选实现先在共享树外测试。
- `local-dev.sh` 当前固定使用 `quantmind-dev` 项目/容器名和独立卷，并不是现成的“每个 worktree 自动一套全栈”。不能从多个 worktree 盲目启动它。单元/契约测试先用临时资源；需要候选全栈联调时，实施一个最小的本地专用启动扩展，让入口接受经过验证的候选源码路径，并使用明确端口、容器、卷、网络、快照和去除生产凭据的配置。候选变更不先同步至云端，配置保留在同步排除目录；发布前验收实际挂载。该扩展目前待实现，不能声称已有支持。

现有沙盒共享 `.env.local` 与 `config/runtime.env`，不能当作无生产凭据的测试容器。Tushare 离线/契约测试使用独立配置及脱敏夹具；真实账号能力与生产小样本在云端受控作业中验证。机器角色和路径写在对应 Compose 覆盖层，不写入两端共享密钥文件。`QM_NODE_ROLE=sandbox`、关闭新增上游采集/beat 与只读镜像挂载需同时验证；训练/Agent 子容器也检查真实挂载和 Docker context，父容器标记不能替代这些检查。

端口切换也纳入开发验收：`start` 卸载云端隧道，使 8000 指向本地；`stop` 保留沙盒数据并恢复云端隧道。Vite 3000 可保持同一页面，但切换前结束交互和任务，切换后刷新并确认后端身份再写数据。`start` 不是热重启命令，不能重复启动；本轮不启停已有服务。

Mac 到 Linux 的依赖分别安装。Mac 当前后端镜像为 linux/amd64，在 Apple Silicon 上有架构转换开销；发布必须追加 Linux 容器内的解析、Parquet/数据库兼容和任务运行验收。虚拟环境、node_modules、构建产物和数据库物理卷不跨平台复制。

换端交接：结束当前端的同文件编辑 → 等 Syncthing 完成 → 检查冲突和内容哈希 → 通过 Git 传递提交并核对 HEAD/分支 → 从 Mac 完整预检。保留并行修改；源码同步、Git 提交、服务重启、数据镜像四件事分别验收。

**2.2 全量采集范围**

- 默认历史范围为各端点及当前账号实际允许的最早时间至最新完整窗口；不得统一截到近 30 天或近一年。按分区拆成可续跑任务，容量/调用预算限制每批工作量，不删除剩余队列。
- 标的包括当前与历史标的、退市证券、终止基金、到期合约及代码变更映射；不能只用当前上市列表循环。无标的、行业级、全市场级文本也纳入，避免只按股票切分漏掉。
- 新闻覆盖全部实测可用来源，研报覆盖全部可用类型、机构与行业，政策覆盖可枚举机构/类型。上游无法枚举的筛选集合要登记完整性风险，优先使用不限制该维度的全域查询。
- 每个端点按文档显式请求全部可用字段；字段限制分批请求时按验证过的自然键和版本对齐合并。原始返回保留未映射字段与数据类型，新字段告警而非丢弃；高权限字段失败只标该字段缺口，不放弃其他可用数据。
- 公告研报目标保存全部已取得记录对应、实际可下载的 PDF/附件，以及 HTML、正文、引用与解析结果。下载失败和未解析各自有队列，不以“已有链接”算全文到本地。
- 只提供当前状态或短保留窗口的端点，有权限并通过最小验收后优先开始留存，从接入日起积累；不能等多年历史回填完才启用，也不能伪造过去快照。
- 与 QuantDB 重叠仍存独立的 Tushare 来源数据，形成可比较查询视图；相同端点别名、完全相同内容可去重，但映射和来源证据不能删除。

**3. 接入位置和最小结构**

文本路径：Tushare → 云端采集作业 → 原始响应/PDF → 标准化文档版本 → PostgreSQL 查询索引 → API、Agent 原文检索 → 独立摘要/研究产物。

结构化数据路径：Tushare → 原始响应 → 按接口/市场/日期或报告期组织的版本化 Parquet → 数据目录和 DuckDB/Arrow 查询 → API、研究脚本、训练输入。原始字段完整保留，标准化视图增加代码、单位和时间口径；不把所有表强行压成行情 symbol/trade_date 键。大体积历史主要存文件，PG 保留必要索引和业务读取表。

沿用 PostgreSQL、现有 Python 依赖、Celery 与运行时密钥模块。首轮不增加消息系统、搜索服务、向量数据库或独立采集微服务。现有 SDK 固定版本为 `tushare==1.2.89`，实施时验证目标端点和超时行为；仅在确有兼容性缺口时调整依赖或改用项目已有 HTTP 客户端。

建议新增少量模块，文件名可随仓库最终审计调整：

| 位置 | 责任 |
|---|---|
| `backend/shared/tushare_client.py` | 运行时密钥读取、显式 fields、超时、脱敏错误、接口能力、限流与重试 |
| `backend/shared/research_documents.py` | 文档/版本/批次入库、原文定位、公司/行业/日期与 as-of 查询 |
| `backend/scripts/tushare_sync.py` | 手动探测、限定窗口采集、失败重跑、有限回填；CLI 与 Celery 共用入口 |
| `config/data_sources/tushare_catalog.json` | 全目录、权限、字段与分区契约；不含密钥，实际运行状态另存云端 |
| `backend/shared/tushare_datasets.py` | 结构化数据按端点自然键版本化发布，统一过滤查询；每接口差异通过经过验证的契约处理 |
| `backend/services/api/routers/research_documents.py` | 受鉴权的只读检索与证据读取；Agent 复用相同查询逻辑 |
| `data/upgrade_v<下一版本>.sql` | 版本化数据库迁移；实施时核对最新版本避免与并行任务冲突 |
| 现有 `celery_tasks.py` / `qlib_app/celery_config.py` | 手动验收后注册唯一云端调度；保持新开关默认关闭 |
| `scripts/tushare_snapshot.py` | 全部 Tushare 数据集、原文与状态清单的发布/拉取/校验，复用既有 SSH、rsync 和原子发布约定 |

预计最少需要四类持久化记录：

- 文档版本：`document_id/version_id`、供应商与接口、供应商自然键/原代码、标题、类型、事实正文引用、来源 URL、内容哈希、原始响应引用。
- 文档关联：一篇文档可关联多家公司/行业；保留供应商行业名、分类体系和关联来源。模型推断关联单独标记，不直接变成历史成分事实。
- 采集批次/窗口：接口、来源/标的筛选、请求字段、时间窗、状态、返回数、分页/切分信息、错误类型、完成时间、输入和产物校验、连续完成水位。持久记录不依赖 Redis 的 6 小时进度 TTL。
- 派生加工：文档版本、摘要/标签、模型与提示版本、生成时间、引用片段；与供应商原文及供应商摘要分开。

优先用供应商 ID 或规范化 URL 形成稳定文档键；缺失时使用接口专属的机构、标题、日期、标的等组合键，并标识可靠性。版本键以内容及相关元数据哈希为基础；重复拉取只增加批次观察记录，不复制版本。无稳定标识时不能保证自动识别全部修订关系，疑似关联单独标记，不按标题强行覆盖。

原始响应与文件存放于云端 `project/data/tushare/`：原始请求批次、按 SHA-256 定位的文件、解析产物分目录。现有 Compose 的数据入口为 `/data`，所以新增可配置数据根在云端容器设为 `/data/tushare`，不要写到未挂载的 `/app/data/tushare`。Mac 沙盒的 `/data` 来自 `.local-dev/project/data`；独立测试则显式使用临时路径，禁止路径缺失时回退云端或主工作树。原始请求留接口/参数/fields，剔除 token 和认证头。先写临时文件、校验并原子重命名，随后事务提交引用；失败可留下待清理孤立文件，但不能出现已发布数据库行指向未完成文件。

所有数据集至少具有目录发现、schema 读取、日期/标的/字段过滤、来源与版本返回、Parquet/JSONL 导出及本地查询能力，避免归档后无法使用。财务、行情、行业、ETF、宏观、事件等分组分别提供一个实际消费示例；每个数据集有 `query_ready / research_ready / training_ready` 等独立状态，不能把可下载一律当作可训练。训练数据集继续经过时间对齐、缺失处理和固定输入验收，外部文本不直接触发交易。

API 支持 `symbols`、`industry`、`document_type`、`start/end`、`as_of`、关键词和分页；返回文档版本、原文路径/链接、页码或片段位置、时间精度、正文状态和数据覆盖。首轮使用 PG 过滤及标题/正文关键词检索，按实测规模决定是否加中文全文索引。Agent 必须实际调用一次检索并引用已存原文；仅登记工具或生成流畅回答不能通过验收。真实云端验收优先在云端容器内执行，跨端查询前核对当前模式及隧道目的地；本地服务和隧道按开发阶段需要切换，不把只读检查当启停要求。

Huntly 保持既有 RSS 数据源。新文本先从独立查询入口消费，复用实体匹配等纯函数；不伪造 Huntly ID、不直接写 Huntly SQLite。后续合并资讯界面时保留 provider/document_id 命名空间。外部正文和 HTML 按不可信数据处理，下载限制协议、目标地址、重定向、大小与超时，正文不产生执行指令或交易动作。

**4. 时间、修订与完整性规则**

- 分别保留事件/报告期、供应商发布时间、发布时间精度、首次获取、版本首次观察、供应商修订时间。缺字段即为空，并记录原因；存储时规范化时区，同时保留原时间字符串。
- 只有日期没有时刻时，不默认设为当天 00:00。历史日频研究保守地在该日期结束后/下一适用交易时点使用；无法判断发布时间的数据不进入严格历史样本。
- 严格系统回放同时约束发布时间和版本首次观察时间。今天抓到的历史文本，不宣称当年系统已经知道；允许另建“按公开发布日期重建”的研究视图，但须标记历史版本/PIT 未验证，不能与真实系统回放混用。
- 文本修订追加版本；旧版本保持原内容。公司行业过滤需说明当前关联或历史有效关联，不能用最新行业归属替代历史分类。
- 窗口状态区分成功有数据、成功为空、疑似截断、无权限、限流、上游错误。空结果只证明该筛选窗口为空，不能据此宣称整个历史数据集完整。
- 请求达到接口条数上限时按文档支持的维度递归切分；最小窗口仍满、缺少完整分区枚举或无法证明取全时标 partial，水位不越过它。没有接口支持证据时不编造 offset 分页。
- 任务使用云端单写锁；并发启动应拒绝或排队。稳定窗口键与数据库唯一约束保证重试幂等。采用有上限的指数退避与抖动；权限错误不反复重试。
- 元数据采集、文件下载、全文解析各自记录状态/完成水位。元数据已齐但 PDF 失败可以继续后续元数据窗口；“全文已覆盖”指标必须保持未完成，失败 PDF 独立重试。
- 初始按接口设置重叠回看窗口，建议日频文本回看 7 天；深证等问答按回复时间补采。无法证明只修改近期历史时，增加有限分段复查，不能声称 7 天回看捕获所有历史修订。

**5. 远端同步方案**

本地同步默认范围为 `all_published`：云端所有已发布、属于本次 Tushare 采集范围的数据，而非选定自选股或近期样本。结构化数据、原始响应、文本、PDF/附件、修订历史、目录/schema、覆盖和失败清单均在范围内；已经生成的派生结果也同步并保留其模型版本。日志中的密钥、运行锁、任务队列和临时半成品不属于数据副本。同步清单必须明确列出这些非数据项，禁止用隐藏排除规则省略已采集数据。

| 对象 | 方向与机制 | 规则 |
|---|---|---|
| 源码、文档、Skills | Mac ↔ 云端，沿用 Syncthing | 同文件单端编辑；独立 worktree 先测试，选无活动任务窗口集成；Git 元数据独立传递并核对 |
| 共享密钥 | 沿用受忽略配置与现有加密同步 | 使用 `runtime_secrets`；共享 token 不表达机器角色，机器角色由部署覆盖层决定；隔离测试不加载生产密钥 |
| 结构化数据/原始响应/PDF/文档 | Tushare → 云端唯一采集者 → Mac 版本副本 | 云端采集并发布，Mac 全范围接收；不加入源码同步、不覆盖 QuantDB 历史 |
| Mac 开发与在线访问 | 默认本地全栈开发；需要核验正式数据时显式切换云端隧道 | 本地查询固定副本，业务写入沙盒；云端查询读取正式数据；在 UI/验收记录中标记后端角色和输入版本 |
| 本地完整 Tushare 副本 | 云端 → Mac，首次全量 + 后续自动增量 | 完整目录及版本清单 + Parquet/JSONL + 全部原始文件，SSH/rsync 续传；数据集逐个校验发布，汇总记录全局完整状态 |
| 完整应用灾备 | 沿用 `dual_node_snapshot.py` | 需要维护窗口；不为每次文本更新触发约 68 GB 的完整快照 |
| Mac 实验结果 | 本地隔离保存，云端按固定输入重跑 | 不通过 Syncthing 回灌正式 `results`，不合并两套数据库 |

Tushare 全量副本与增量分发是待实现能力，不能与当前已存在的完整应用快照混为一谈。增量包减少每次传输量，保留的逻辑数据范围仍为全量。建议按以下协议实现：

1. 云端导出全部已提交、已发布的版本。文档用 PG 一致性读事务取得版本集合与文件引用；结构化数据取原子发布的分区清单，逐数据集固定版本后形成全局 manifest。不同数据集的截止时间分别记录，不虚构全站同一业务时间点。
2. 以显式版本集合形成新 release，记录 `release_id`、上个 release、schema 版本、导出代码版本、完整范围、逐数据集截止时间、窗口覆盖及每个文件 SHA-256/字节数。分区清单复用不可变子清单，避免每轮重写整套历史大清单。
3. 增量通过本次与上个已发布清单的版本集合差异计算。不要仅用 `MAX(id)` 当事务提交水位：并发事务可能分配较小 ID 后较晚提交，单纯数值游标会漏数据。
4. 文件按内容哈希不可变保存；导出时核对全部引用存在。先写 `.building`，清单/数据/文件齐备且校验后才发布 `COMPLETE`，原子切换数据集专用 `latest`；无需暂停 QuantDB、Huntly 或训练。数据集 COMPLETE 表示对应发布清单齐备，历史取全状态仍单独判断。
5. 冒烟测试发布小包；生产首次镜像覆盖全部已发布数据，历史回填中新发布的分区持续加入同步队列。后续只传变化记录和缺少的内容哈希文件；逻辑删除/撤销以版本化状态传递，不靠 rsync 删除模拟业务含义。
6. 云端导出区建议放 `/root/data/disk/quantmind/exports/tushare/`，仅存发布清单与必要增量，不复制第二套原始文件；引用的内容对象来自不可变数据区。Mac 放 `logs/tushare-mirror/`：共享 `objects/` 保存去重内容，`releases/<release-id>/` 保存固定版本清单，本地查询索引单独管理。该范围已由源码同步规则排除；它是长期数据副本，不得按普通日志清理。
7. 拉取中断保留暂存和上一份可用 release；恢复后只补缺失字节/文件。逐文件校验、schema 检查及版本依赖检查通过后原子发布；缺父包则先补父包或取得完整 manifest。大回填期间已验证的数据集可独立查询，但全局镜像必须展示未同步数据集及字节数，不能显示全部完成。
8. 研究固定 release ID；与 QuantDB 联合研究同时记录 QuantDB 快照 ID 和 Tushare release ID。完整应用的 `logs/cloud-snapshots/latest` 不跟随 Tushare release 更新；副本不覆盖本地旧库或正在使用的沙盒。Mac DuckDB/Arrow 查询本地文件，文档索引可从导出重建；开发应用通过显式配置指向只读副本。
9. 手动验收后，本地自动同步是正式交付项，默认在线每 15 分钟检查一次、唤醒/重连后补同步；首次全量允许持续续传。采用独立 Mac 同步服务且全程单实例，复用既有 SSH 身份与主机校验；不需要常驻聊天任务。仅数据传输在 Mac 运行，上游采集仍在云端。本次只是计划，不安装调度。
10. 保留完整输入清单。磁盘清理按无实验引用、无版本依赖的条件单独执行；不默认按最近 30 天删除，也不改其他项目的同步任务。容量预算保留现有 100 GiB 恢复余量，并计入生产、快照与导出实际物理占用。

本地镜像与沙盒联调采用独立只读挂载，例如把固定 release 的清单及其内容对象映射到容器 `/tushare-mirror:ro`，具体绑定由本地覆盖层控制。查询根与采集输出根分开；本地重建的检索索引及实验产物写沙盒目录。镜像同步器可在后台添加新对象/版本，但正在运行的测试、训练和 Agent 固定旧 release，不在查询时追随 latest。同步器直接走 SSH/rsync，不依赖 8000/18080 隧道，因此启动本地全栈、卸载 API 隧道不应中断数据镜像；这一场景须实测。

云端历史回填按现有 Celery 作业拆成有限批次、持久化检查点，由云端服务接续，不绑定 Mac 终端或 SSH 会话存活。Mac 断网、休眠或更换开发端不终止云端采集；重连后的本地同步按已发布清单补齐。对 worker 重启和代码发布保留可恢复窗口，避免部署后丢失未完成进度。

发布时须确认云端新原始数据目录被现有 runtime inventory/完整快照覆盖，导出清单不造成嵌套重复；数据副本不经 Syncthing，`.local-dev` 必须显式禁用新增 Tushare 上游采集调度。不得只依赖“当前没 token”阻止本机采集。

容量控制：用户已认可云端按需扩容，当前磁盘大小不作为减少接口、历史、字段或原文范围的理由。P0/P1 用实际样本估算每数据集历史行数、压缩字节、PDF 大小、去重率及版本增长，计入快照、导出、传输暂存和本地索引。按回填批次推进逐步校正预测，不盲目一次采购最大规格。

云端可用空间须覆盖“下一回填批次 + 未来 30 天预测增长 + 快照/暂存峰值 + 恢复余量”，恢复余量至少维持现有 100 GiB。预测不足时在该批次启动前安排扩容，按云厂商支持的规格选择满足预算的容量；涉及计费的实际单价与预计新增费用在执行时核实并记录。扩容等待期间暂停无法容纳的历史批次，持久化队列，尽量继续已有增量；扩容完成自动续跑，不静默缩减范围。

扩容实施先确认云厂商、目标磁盘 ID、挂载点及可恢复备份，优先扩现有数据盘；核对云盘容量、分区（如适用）、文件系统扩展、UUID 与 `/root/data/disk` 挂载路径、目录权限和容器卷映射。扩容前后记录数据清单校验与云端健康检查，再完整运行双端预检。若厂商要求停机，则选择无活动训练/研究的维护窗口；保留失败恢复入口，不在磁盘尚未扩展成功时推进采集水位。本次仅更新计划，不触发计费操作。

Mac 当前约 2.8 TiB 空间也要持续测算；若本地完整副本将超容量，应在耗尽前报告所需本地存储，保留待同步清单，不能偷偷改成仅缓存近期数据、只保存链接或删除历史。云端扩容不改变云端唯一采集主节点和 Mac 完整副本的角色。

**6. 分阶段实施和验收门槛**

| 阶段 | 执行范围 | 完成证据 |
|---|---|---|
| P0：全目录、权限与容量 | 重新双端预检；确认活动任务与 worktree 基线；安全读取 token；枚举官方完整目录、字段和来源；逐项探测；测算历史容量 | 每个目录项均有状态，无未解释漏项；权限/字段矩阵、目录快照、容量与请求预算；无 token 继续离线工作，真实调用保持未测 |
| P1：公告 + 研报完整链路 | 先落最小迁移、客户端、存储、查询与解析；手工采集限定窗口；至少一份真实 PDF 提取并核对原文，目标公告/研报各一份 | 原始响应 → 文档版本 → PDF/页码 → API → Agent 引用可追溯；相同请求两次无重复，修订保留，未来文本被过滤 |
| P2：通用存储和本地镜像 | 除文本外接通一个真实结构化数据集；验证完整小包与增量包；启用本地数据集发现、离线查询 | 结构化和原文均到本地；断网续传、损坏、版本依赖、并发导出、旧输入固定均通过；无需停止全栈 |
| P3：文本全面覆盖 | 政策、全部可用新闻来源与新闻联播、沪深问答、央行报告及目录发现的其他文本 | 至少九接口分别验收，所有可用来源进入生产队列；PDF 下载和解析缺口各自登记 |
| P4：结构化数据广覆盖 | 按主数据 → 行情财务 → 行业/ETF → 宏观/事件 → 其他资产/特色的依赖顺序实现目录中可用端点；重叠数据分来源保存 | 每项具有采集契约、版本化落地、本地查询及消费状态；无权限或上游限制逐项列出；不改 RRG 配置/登记状态 |
| P5：持续增量与同步 | 每个端点通过手动验收后即逐步启用云端调度和 Mac 自动镜像，优先短保留/不可回溯端点 | 至少两个真实周期及故障恢复；持续更新、镜像滞后与丢失窗口可观测；不等待全部历史回填完成 |
| P6：全历史回填与总验收 | 对所有可回填端点，从账号允许起点到已完成增量窗口分批补齐；全量原文同步和缺口修复；历史修订巡检 | 分接口/字段/标的/来源/分区验收；本地与云端 release 清单完全对齐；不具备取全证据的项目保留 partial |

P1 初始工程验收预算建议：3 家公司、最近 3 个自然日，每类最多保留 100 条元数据、最多下载 5 份 PDF、单次总时长 10 分钟。无样本时扩到限定 30 天或已知有报告日期。以上仅用于验证解析/幂等/同步，不限制生产标的、来源、条数或历史范围。预算耗尽导致的 partial 必须留下未完成窗口。

P3 低频接口使用匹配其发布节奏的窗口；央行选择最近已发布季度的一份报告，而非对最近三天的空结果判定接入失败。

P4 的顺序表示优先级，不是范围筛选：日线、三大报表和所有可用目录项均进入计划。中信/申万分类、价格指数/收益指数、ETF/指数映射需明确体系，不因 Tushare 有接口就解除 RRG 的数据阻塞。数据下载全覆盖和量化可用性分别验收。

P5 建议初始频率：公告每小时，研报每日两次，政策每日一次，新闻每 15–30 分钟遍历全部已授权可用来源，新闻联播每日检查并补迟到数据，问答每日两次，央行每日检查一次。结构化端点按发布节奏安排，盘中端点按权限/保留期单独设置。上述是待实测修正的工程默认值，精确时点按上游更新和现有行情/训练错峰。历史回填、近期增量和修订重查共享账号限流预算，增量优先，回填检查点持久化，可中断恢复。

P6 属于本计划必交付范围。先完成容量和吞吐测算，再按端点/年/月/日等窗口顺序执行，批次上限只决定每次推进量。对停更端点回填至停止日期；对从未保存的实时历史、不可下载旧文件等保留永久缺口解释。历史全量检查后仍按周期重扫易修订数据，保存修订版本与观察时间；不凭近 7 天增量推导多年历史无变化。

**7. 验证、部署与恢复**

保留能验证失败边界的测试：重复请求不增版本、同日多篇不丢失、修订不覆盖历史、日期精度与回复时间过滤正确、满页无法取全不推进水位、PDF 失败不冒充全文完成、文件落盘后进程崩溃可重跑、并发任务互斥、下载中断/文件损坏不发布新 release。数据存储验证用临时目录/独立测试数据库，Mac 不连接生产 DB/Redis。

开发与发布顺序：识别宿主/context并按宿主预检 → 独立 worktree 编码和隔离测试 → 必要时经明确候选源码挂载做 Mac 全栈联调 → Linux 隔离容器兼容验证 → 明确提交本次文件。进入包含发布的实施阶段后：确认无活动研究/训练任务 → 在受控窗口集成共享工作树 → Syncthing 同步并处理冲突 → Git 独立对齐提交及 HEAD/分支 → Mac 完整预检及云端角色/挂载核对 → 云端按版本执行新增 schema → `sudo -n bash scripts/dual-node.sh cloud-compose` 重启相关服务 → 云端真实小样本验收 → 启用新调度 → 观察增量与 Mac 镜像。若增加依赖则在云端重建对应镜像；纯代码按现有 bind mount 发布流程处理。编写计划、修改文档和提交代码本身均不触发构建或重启。

由于共享代码会进入运行中的 bind mount，集成窗口要早于复制代码；不能同步实验代码后再声称尚未发布就绝不会生效。新功能默认关闭，迁移尽量只做向后兼容新增。

失败恢复先关闭新调度并保留采集批次、原始响应和失败窗口，再回滚相关代码；不要删除新数据表/旧版本或把 Mac 快照覆盖回云端。迁移失败与采集失败分开处理，重复执行前验证当前版本状态。

**8. 最终交付清单与完成定义**

- 全目录账号权限/能力矩阵：至少九个文本接口以及全部结构化目录项；含 API/来源/字段/标的范围、权限状态、历史起点、窗口缺口、时间精度、原文/解析/本地/消费证据。
- 数据契约与迁移：内部前缀代码、供应商原代码、单位与分类体系、自然键、版本、时间可见性、连续水位和覆盖定义。
- 公告与研报完整链路验收报告；其余文本逐类样本和业务消费证据。
- 云端部署与调度说明、手动补窗/恢复入口；清楚标记哪些已上线、仅代码完成、受权限阻塞。
- 全量数据镜像清单、Mac 自动同步状态、断网/重连和校验报告；结构化与文本离线查询示例，联合研究固定输入说明。
- 全历史回填计划及执行报告：实测行数/原文大小/去重率/吞吐推算的容量、请求量与时间；逐批检查点、完成量、剩余量、失败和永久缺口，不能只交估算后不执行。

**8.1 不遗漏的独立验收指标**

| 指标 | 计算与完成要求 |
|---|---|
| 目录覆盖 | 已明确处置目录项 / 已发现目录项 = 100%；待实现仍计入总数，权限未知单列 |
| 账号可用接口接入 | 具备采集、发布和本地查询的可用接口 / 全部实测可用接口；目标 100%，原始归档与业务消费进度分列 |
| 历史窗口覆盖 | 已验证完整窗口 / 实际应查询窗口；逐标的/来源/周期统计。确认为非交易日、上市前或无事件的窗口记录依据，不制造缺失值 |
| 字段覆盖 | 可获取字段是否均请求并留存；默认隐藏、字段权限不足和新字段分别核对，标准化未映射不等于原始可丢弃 |
| 原文覆盖 | 成功下载 / 应下载文件；成功解析 / 已下载文件；未知链接和坏链单列，二者不能合并为一个“接入成功”比例 |
| 本地镜像 | 对固定云端 release：文件/对象/分区集合无缺项，字节数与 SHA-256 一致；本地行数/自然键/schema 与发布清单一致 |
| 新鲜度 | 各端点最新上游可用窗口、云端完整水位、本地已验证水位及同步滞后；旧 release 100% 不代表已追平最新 |
| 业务可用 | 每数据集可发现并查询；每主要数据组有真实消费示例；原始、标准化、研究、训练就绪度分别记录 |

离散事件类接口通常没有可独立确认的应有记录总数，因此同时检查参数分区是否穷尽、截断是否解除、边界重叠、上游总数（若有）、交叉查询及抽样对账；仅行数一致、无 HTTP 错误或本地文件哈希一致不能证明上游本来就没有漏数据。明确区分“没有漏传云端已发布数据”和“已证明取全上游所有历史”。

首个里程碑 P0–P2 证明链路与镜像可行；完整目标为 P0–P6 对账号可获取范围验收完成，并对所有其他目录项给出明确状态。不能以两个文本样本或部分近期镜像作为本需求完成。任何容量、权限或上游质量造成的未完成项必须出现在最终清单，不能悄悄缩小范围。
