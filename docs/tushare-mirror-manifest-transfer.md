# Fixed manifest transfer and timeout diagnosis

The Mac log ended in two `TimeoutExpired` records with no stage and empty stderr. Its latest downloaded manifest was79,419,571bytes; a30second uncompressed SSH command requires about2.65MB/s just for these bytes, excluding connection/setup. This makes manifest transfer a plausible cause, but the old type-only logs cannot prove which call timed out.

A separate read-only `/tmp` transfer on2026-09-09 pinned `data-630dbb0ca721022e19d02337cc578d3cd5b4f61f797fa31f900ed192be36f278`: pointer0.635s, compressed rsync manifest11.941s,86,253,968uncompressedbytes, full SHA matched. It did not run mirror(), acquire the client mirror lock, install code or change CURRENT. Evidence is `/tmp/tushare-manifest-transfer-readonly-report.json`; this one transfer is not a whole-mirror performance claim.

The candidate keeps small CURRENT SSH fetching at30seconds and pins the release/hash before any path construction. It reuses a locally SHA-verified fixed manifest or archives alias. Missing manifests use the existing rsync compression settings in a private temporary directory,15second SSH connection timeout,45second rsync inactivity timeout and180second subprocess total deadline. Full SHA must match both pointer and release identity before atomic replacement into releases; the original manifest parser still validates its structure. Partial/wrong/symlinked transfers never advance CURRENT, and retry starts with the current remote pointer. Temporary partial bytes are cleaned on normal exceptions, so this small manifest stage restarts instead of maintaining a new resume protocol.

All manifest-listed objects, observations, archives and attachments still follow the existing complete transfer and SHA verification. No history or file classes are omitted. CURRENT is published only after the complete closure passes. The large object transfer retains existing rsync resume/inactivity behavior;180seconds bounds only manifest transport, not an entire growing archive mirror. A transport deadline does not solve arbitrarily large manifest parsing or total metadata growth.

Failure JSON now includes a safe stage, elapsed seconds and timeout/return code when available. It never includes subprocess command text, stdout/stderr payload or credentials. Stages distinguish pointer_fetch, manifest_prepare/transfer/verify/validate, objects_transfer and objects_verify. Existing schedule/venv installation is unchanged; the parent must deploy/reinstall the client copy through the established path before its LaunchAgent can use the fix. This candidate does not restart that agent or launch a mirror.

Offline temporary fixtures cover compressed command bounds, exactly pinned manifest paths, partial timeout cleanup/retry, SHA and symlink rejection, archive/local reuse and inode preservation, object-transfer failure retaining old CURRENT, full object/attachment verification, and pointer timeout classification. Existing mirror acceptance fixtures retain their recovery/corruption assertions with only transport mock updates and the extra local manifest SHA-check count.
