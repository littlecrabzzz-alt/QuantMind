# 推理与模型选择合同

用途：解释训练产物如何成为可消费模型、模型切换优先级及推理故障定位。训练操作见 [模型训练指南](QuantMind_模型训练完全指南.md)。

## 注册与身份

`backend/shared/model_registry.py` 管理 `qm_user_models` 与 `qm_strategy_model_bindings`。用户模型和策略绑定按 `tenant_id + user_id` 查询；不要通过伪造身份请求头测试别人的模型。模型状态和产物可用性必须同时核对，训练任务成功不等于模型已同步到可加载位置。

常用产物路径为 `models/users/{tenant}/{user}/{model_id}`；注册记录中的 `storage_path/model_file` 才是该模型的加载依据，不把旧 `models/production/model_qlib` 当所有用户的模型位置。产物包含权重、元数据及实际训练特征/目标信息。目录应按实例实际模型挂载定位。

仅加载可信模型。哈希用于完整性比对，不会让 pickle/joblib 等反序列化自动变安全。

## 生效模型选择

统一入口为 `resolve_effective_model()`，Celery 等同步路径使用 `resolve_effective_model_sync()`：

1. 显式 `model_id`：先尝试匹配生产目录模型，再尝试当前用户可用模型。
2. 指定策略的可用绑定。
3. 用户默认模型。
4. 只有显式配置 `PRIMARY_MODEL_ID` 且主模型目录存在时，注册解析器才可能返回配置的系统模型。
5. 无可用模型返回 `not_found`，不是隐式加载 `model_qlib` 或 `alpha158`。

显式用户模型未就绪时，注册解析器会继续尝试绑定/默认；不能仅凭请求中的 ID 推断实际生效模型。读取返回的 `effective_model_id`、`model_source`、`fallback_used/fallback_reason` 与错误。

推理脚本/路由还接收显式主备模型及目录配置；这不等于存在默认系统兜底，也不保证用户模型失败会自动回落。不要为了绕过模型注册错误临时指定历史系统模型。

## 用户态管理接口

基路径 `/api/v1/models`，由 `backend/services/api/routers/model_training.py` 提供：

| 方法与相对路径 | 用途 |
| --- | --- |
| `GET /` | 查询当前用户模型 |
| `GET /default`、`PATCH /default` | 查询/修改默认模型，注意市场参数 |
| `GET /strategy-bindings/{strategy_id}` | 查询策略绑定 |
| `PUT /strategy-bindings/{strategy_id}` | 绑定可用模型 |
| `DELETE /strategy-bindings/{strategy_id}` | 解除绑定，之后按默认等规则解析 |
| `POST /run-training`、`GET /training-runs/{run_id}` | 提交/跟踪训练 |

推理入口为 `POST /api/v1/inference/predict`；具体请求字段、认证及输出以当前 API schema 为准。自动推理和单次交互推理不是同一个执行场景，不将成功的单次请求当自动任务验收。

## 主要执行路径

- `backend/services/engine/inference/router_service.py`：解析用户/策略模型并路由推理。
- `script_runner.py`：脚本式批量推理、日期与数据路径处理。
- `model_loader.py`：按模型框架与元数据加载产物。
- 自动推理产物写入 `engine_feature_runs/engine_signal_scores`，并通过完成标记与最新信号版本供后续任务消费。应核对实际 `run_id`、预测日期和用户，不把旧信号当本次成功结果。

## 排错顺序

1. 记录请求身份、市场、策略、显式 ID 以及实际生效模型。
2. 检查模型注册状态、路径、权重、依赖和特征顺序/维度。
3. 检查目标日期的数据覆盖、复权和标签周期；缺列/空股票池不能伪造分数。
4. 查看该次运行日志与落库结果，区分加载失败、数据失败和结果未消费。
5. 模型切换后核实新产物的模型 ID、日期和信号版本；不要清空全库或重启整栈来掩盖路由错误。

推理分数不是保证收益或成交价格；实盘授权、风控、订单回报与对账由独立交易链路负责。
