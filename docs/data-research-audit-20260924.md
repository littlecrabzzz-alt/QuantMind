**QuantMind：数据同步到研究使用的审计与优先级建议**

后续已接手实施。本文保留 9/24 初始审计的时点结论；已修复项、当前数据水位及两端固定输入验收见 [9/25 实施记录](research-data-priority-20260925-result.md)。

审计时间：2026-09-24 晚间，Asia/Shanghai。核对 Mac 主树、原生 Tushare 归档、两端运行容器、只读 SQLite/PostgreSQL、实际 Parquet、Qlib 日历与协调记录。数据持续变化，具体数值以采样时间为准。机器可读采样见 [审计证据](./data-research-audit-20260924.evidence.json)。本任务只新增分析文件，没有改采集配置、重启服务、调用供应商或启动模型研究。

核心判断：当前已经有大量数据与部分可用研究工具，但“全量归档建设”占据了推进主线。研究所需的近期数据、固定课题输入、研究执行器与成果验收之间仍有断点。继续等待 Tushare 全历史完成，不能自动解决这些断点。

用户最新方向：区分重点与非重点，先推进研究需要的数据。用户对首个研究方向回复“都可以”；本报告据当前准备程度选择 **A 股量价闭环优先，RRG 行业信号随后推进**。这不代表已经批准或启动具体训练/回测。应把优先级落实到“课题 × 数据集 × 标的集合 × 时间窗 × 字段和口径”，而不只是把某个供应商整体设为高优先级。

| 链路 | 当前实际路径 | 核验结果与限制 |
| --- | --- | --- |

| Tushare 云端供数 | Mac 固定 release → 12 API 研究子集 → SSH 私有通道 → 云端缓存 → 应用读取 | 审计初始云端 CURRENT 最后成功写入为 09-20 05:30；Mac 已有 09-24 release。供数与清单大小故障正在由另一任务修复，不能把补丁合入当成新版本已切换。 |

代码同步、完整数据库恢复快照、QuantDB 日常更新、Tushare 发布、研究输入版本分别推进。Mac 完整业务基线仍是 09-08，这并不等于行情也停在 09-08；反过来，行情更新也不等于研究输入已经更新。

**2. 已确认的阻塞与成本来源**

**A. 云端供数存在真实工程故障，不能只归因于网络。**

- 旧供数入口收到 CURRENT 请求后，在响应前准备整个研究子集；随原始 release 更新，需校验十几万个分区。SSH 中断、休眠和长准备时间互相叠加。
- 09-24 已生成的研究子集 manifest 为 85,659,745 字节（81.69 MiB）；旧云端 manifest 下载硬上限为 64 MiB。日志中累计可见 85 条 `ValueError: Transfer exceeds reservation`，23:13 的最新失败也明确落在 manifest 下载调用。
- 这不是云端 50 GiB 缓存预算耗尽：旧成功缓存约 5.45 GB，云盘当时尚余约 515 GiB。
- 并行任务在本次审计中合入 `77d57be6`（先服务已验证版本、后台刷新并披露滞后）与 `af7df927`（manifest 有界提高到 512 MiB）。该任务拥有供数文件和发布窗口。本审计不重复修改；需要以最终 CURRENT、源 release、真实查询和失败恢复验收，而不是 Git 提交验收。

相关实现：[供数与拉取](../scripts/tushare_research_cache.py)；并行协调记录：[供数恢复](../coordination/tushare-data/20260924T150749Z-mac-research-cache-production-start.md)。

**B. 近期行情受到规划顺序阻塞，增加下载并发不能解决未入队的任务。**

- 对已完成任务选取最新日期，并实际读取对应 Parquet：Tushare daily、adj_factor、daily_basic 均到 09-18；fund_daily、sw_daily 到 09-23，CI005001.CI 样本到 09-23。这里不宣称整个行业集合完整。
- `recent:structured` 当前游标为 6000。使用同一份只读规划快照和现有生成器重放，近期 daily 首项在位置 6243，adj_factor 在 6250，daily_basic 在 6257；前面包含财报根请求与 5916 个股票名称历史请求。
- 核对 09-23、09-24 epoch 时，未见这三个 API 在 09-19 以后的近期日期任务。代码中近期行情位于 namechange 的全股票循环之后。这是“近期优先”在整体生成器顺序上没有落实到核心行情的具体证据。
- 已有独立近期补采只覆盖部分 market API，未覆盖 structured 的 daily/adj_factor/daily_basic。应扩展既有近期准入逻辑，先保证研究核心日期，再让历史游标推进。

相关实现：[structured 规划](../backend/shared/tushare_structured_contracts.py)、[market 近期规划](../backend/shared/tushare_market_contracts.py)、[主调度](../backend/shared/tushare_pipeline.py)。

**C. 全历史队列仍在增长，当前没有可承诺的全量完成日。**

- 日志采样：09-19 初期 pending 约 268.7 万，09-24 23:08 约 350.8 万；期间记录了约 75 万次请求，队列仍净增加约 82 万项。任务展开和新规划使分母持续改变。
- 大类待采约为：research_extra 79.3 万、market_sentiment 44.3 万、text 36.8 万、technical_extra 30.3 万、equity_event 27.4 万、factor_library 26.6 万。类别名字带 research 不代表被当前课题依赖。
- 文档约 890 万待下载、151 万已解析；原始下载成功、解析成功、时间可得性通过和研究可消费是不同状态。
- 现有历史起点广泛设为 1990，领域包含期货、期权、海外、宏观、筹码、文本等。全量归档有长期价值，但其任务数不适合作为研究上线门槛。
- 快照中的 done/empty 是任务状态，不能据此算供应商历史完整率；被 superseded 的约 581 万任务主要是规划替换痕迹，也不是新增数据量。

**D. Mac 归档节点的连续性与文档成本需要分开治理。**

- 日志存在约 41 小时没有完成周期的区间，不能只凭日志判定全部由休眠造成；另查 09-24 电源日志，确有大量 Sleep/DarkWake 与晚间开盖恢复记录。Mac 休眠时无法保证采集和供数持续在线，这是当前节点选择的直接约束。
- 正常周期最近约 108–117 秒，一轮异常为 791 秒，其中文档 790 秒、处理 0 个阶段。后续正常轮恢复到约 1100 个阶段，不能把这个异常值当稳定吞吐。
- 独立确认一个性能缺口：终态重试针对每个选中文档前后统计 document_attempts，但该表约 350 万行，没有 document_id 查询索引；EXPLAIN 为全表扫描，单次只读计数 3 秒未结束而被审计期限中断。16 个重试对象可触发 32 次计数。它是可验证的成本放大点；尚未把 790 秒逐阶段归因到它。
- API 与文档在单轮中并行，主循环仍等待二者结束才开始下一轮。文档预算超时会拖延下一轮结构化采集。应先修边界和索引、独立计时，避免仅堆更多下载进程。
- 当前 Mac 空闲约 1.1 TiB，采集未触发 300 GiB 保留线。此刻的主要问题不是磁盘即将满。

相关实现：[原生 worker](../scripts/tushare_archive_worker.py)、[文档处理](../backend/shared/tushare_documents.py)。

**E. QuantDB 原始行情与 Qlib 派生数据没有在云端同步到同一水位。**

- 两端应用容器执行现有 `resolve_qlib_provider_uri('CN')`，均返回 `/app/db/qlib_data`；云端日历最新 09-18，Mac 最新 09-22。实际云端 daily_forward/daily_unadjusted 分区已经到 09-23，最新分区各 5568 行。
- 因而“云端已同步行情”不能证明使用 Qlib 的训练或推理已获得新行情。具体失败发生在哪一次构建，本审计没有取得完整日志，不猜测异常类型。
- 当前 `update_qlib_cache()` 捕获失败后返回 error，而 CLI 末尾仍可记录“Qlib 缓存完成”并返回 0。这是会掩盖派生失败的代码路径，需要以各阶段结果决定最终状态。
- Mac PG 已核验至 09-22、当日 5567 行。云端 PG 的复合只读统计超过 4 秒期限，未将其日期写成已确认值。

相关实现：[QuantDB 日常同步](../backend/scripts/quantdb_daily_sync.py)、[Qlib 构建入口](../backend/services/engine/qlib_data_builder.py)。

**F. 最大的产品缺口：新数据没有成为新课题的固定输入。**

- 两端研究设置相同：100 只股票、8 个量价因子、LightGBM/Top20 模板；训练 2023–2024，验证 2025 年一季度，测试 2025 年二季度，purpose 为 development_comparison。
- Agent 子容器挂载本课题 workspace 和该固定 snapshot。目录中没有自动注册本次新 Tushare release 的通路；改应用 `/data/tushare` 只读挂载不会改变它。
- 两端 PostgreSQL 的 `engine=deepagents` 课题数均为 0。旧研究窗口本地 12 个、云端 3 个；两端普通训练表各有 2 条（1 成功、1 失败），普通回测表各 1 条，最新为 09-05。这里只描述这些已查询入口，不否认外部脚本、历史测试或其他目录中存在研究产物。
- 文档明确：通用 Python 分析可做探索；正式训练回测工具仍受冻结模板约束，任意策略正式执行、独立留出验证、持续向前模拟尚未完整接入。把 Tushare 全量下载完成也不会自动补出这些能力。

相关实现：[Agent 输入](../backend/services/research_agent/settings.py)、[实际容器挂载](../backend/services/research_agent/sandbox.py)、[已有产品能力与缺口](./continuous-research-and-strategy-plan.md)。

**3. 重点与非重点：建议按四层执行**

| 层级 | 数据范围 | 当前研究用途 | 推进规则 |
| --- | --- | --- | --- |
| P0，共用基础 | 股票/指数/ETF 必需行情、复权、日历、基础代码与上市退市状态；按课题补停牌涨跌停/成本字段 | 所有量价研究、信号日期与执行检查 | 先复用已存在且口径符合的 QuantDB；Tushare 负责缺项、对照及明确必要数据。近期核心日期先入队，PG/Qlib/查询一起验收。 |
| P1，首个课题 | A 股量价因子与对照所需行情、成交量额、换手及执行字段；其次是 RRG 中信行业价与分类 | 打通一个新固定输入 → 真实实验 → 可查结果的闭环 | 限定代码、窗口、必需字段；每一批补齐后立即查询、导出、校验并登记课题输入，不能继续只累计归档。 |
| P2，保留时效 | 已明确无法追溯、短保留期数据的必要原始记录；当前课题引用的特定公告/报告 | 避免以后无法补取，以及补充时点证据 | 保留最小必要采集；昂贵正文解析按实际引用推进。不能将尚未核验“短保留”的接口一概升高。 |
| P3，后台归档 | 暂未被课题使用的海外/期货/期权/全市场技术因子/全量文本正文/超出窗口的深历史等 | 长期归档和未来扩展 | 降低资源优先级，保留检查点与已存数据；不作为当前研究门槛。课题明确需要时再升级。 |

重点按三种完成条件分开：基础数据新鲜度满足、课题窗口完整可消费、研究实验有真实结果。三者不能共用一个“同步完成”。

不要只调 group_weights。当前 `structured` 内财报、名称历史与近期日线混在一起，`market` 内基金、债券、期货也混在一起。组权重无法解决任务尚未生成，也无法表达“只给候选 ETF 的持仓补历史”。应优先复用既有单点/窗口批次工具和近期规划，不新增第二套调度服务。

**4. 两个研究方向各自的最小数据清单**

**第一条：A 股量价。** 优先复用现有 QuantDB，按已冻结的研究对象准备原始开收盘、可比复权价/复权因子、成交量额、换手、日历、上市退市、所需涨跌停和停牌信息；原始执行价格与研究复权价格分开。8 个既有量价因子可以作为工程闭环的起点，但应先检查选定新窗口的完整性，不能直接把旧开发测试期重命名为独立样本。暂不依赖财报全文、公告全文、筹码全历史、海外数据或基金全市场持仓。

**第二条：RRG。** 以下沿用现有案例分层推进，不擅自改变研究目标或冻结假设。

| 阶段 | 重点数据 | 边界和验收 |
| --- | --- | --- |
| 信号层 | ci_daily、trade_cal、完整中信一级代码/分类版本与价格口径证据 | 沿用比较窗 2022-09-01 至 2026-08-31；前置 318 个交易日预热、至少 319 个观测；28 个候选行业加明确排除名单；逐日覆盖/唯一性/有限正价/基准口径通过。先形成新的可消费固定包。 |
| 扩散度层 | ci_index_member 的历史有效期与已知时点；成员股票可比复权价、时点市值 | `known_at` 缺失是来源语义问题，不能靠重下同接口补出。单独列证据缺口，不阻塞不依赖成员的坐标与信号诊断。 |
| ETF 执行层 | 候选 ETF 的 etf_basic/fund_basic、fund_daily/fund_adj、上市退市和交易状态；按暴露方法需要 fund_portfolio / etf_sh_cons / etf_sz_cons | 只补已固定候选集合与交易日期。定期部分持仓与 PCF 不能替代；公告时间、原始开盘价、分红复权、单位和可成交约束分别验证。 |

云端当前研究子集仅 12 API，不含 ci_index_member、fund_adj、fund_portfolio、ETF PCF 等。若课题推进到后两层，必须按课题扩展子集；单纯让当前 12 API 追上也不能交付完整 RRG。

旧 RRG state.json 的数据检查停在 09-08，配置仍指向旧 QuantDB 文件形状；09-09 的 Tushare 行业坐标桥、09-10 的 PIT/ETF 桥已有独立技术证据。这说明既有采集成果尚未统一反馈到研究状态。需要重跑有版本的检查并更新证据引用，而不是手工改 blocked_data 为通过。旧报告里的 `known_at=0` 是当时固定输入结论，本审计没有重验全部最新历史成员。

A 股量价闭环推进期间，可以继续只读整理 RRG 信号包及语义缺口；不要求先完成 RRG 的所有 ETF 和历史成员数据，才开始第一条研究。

**5. 按研究可交付性排序的行动与退出条件**

| 顺序 | 行动 | 退出条件 |
| --- | --- | --- |
| 1 | 完成并行供数修复的真实验收；修正云端 Qlib 水位；近期核心行情准入独立于历史展开 | 指定版本能被真实查询；缓存报告源版本与滞后；行情与派生层一致；阶段失败不显示全链路成功。 |
| 2 | 固定一个课题的数据合同：数据集、标的、期间、字段、口径、版本、缺口 | 每个必需输入都有来源和检查；非依赖数据明确退出关键路径；缺口区分数量不足与语义不可证明。 |
| 3 | 从已有归档/QuantDB 生成新固定研究包；只补该包真正缺少的切片 | 用研究执行器的实际 reader 读到正确 schema、日期、代码和行数；输入清单/hash 固定；运行中旧研究输入保持不变。 |
| 4 | 按现有课题批准流程完成一次真实对照实验并保存成果 | 数据版本、代码、参数、基线、费用、结果与失败证据可查；能从平台打开并被下一课题引用。负结果也合格。 |
| 5 | 再扩展到独立验证和向前模拟，背景全历史继续推进 | 独立区间与累计试验有记录；不能把开发期回测或同步完成作为独立有效性/交易许可。 |

应优先展示的运营指标：重点数据最新完整日与延迟、课题必需切片通过数/缺口数、研究包发布时间与执行器可读性、本周完成并留存证据的研究结论。全库文件数、请求次数和总 pending 可保留为运维指标，但不要再用它们代替研究进度。
