## Verified findings

- Assessment logical bytes: raw objects 5,280,626,509; Parquet 1,646,855,200; attachments 586,679,456; documents metadata 5,644,628,091 (6040 files); archives 3,100,437,153 (148 files); releases 3,148,429,783 (149 files). documents + archives + releases ~11.08 GiB. Directory category totals and inode allocation are measured per category, so they do not establish cross-directory inode duplication or pairwise SHA matches.
- archive._copy_manifest (tushare_archive.py:186) writes raw manifest to a NEW temporary inode then links that temporary into archives. It does not link the already immutable releases manifest. The protocol therefore creates duplicate exact bytes for newly retained releases; assessment counts/sizes fit this but are not an audited list of all duplicate pairs.
- publish (tushare_pipeline.py:1872 onward) starts from previous.files, adds ALL old documents/schemas/archives JSON, then retains predecessor only after meaningful candidate comparison. Each new manifest is a full flat inventory plus dataset metadata, not a nested copy of old manifest JSON. Cumulative full inventories grow roughly with release count times inventory size. Average existing release manifest ~20.15 MiB; archives ~19.98 MiB.
- Mirror (tushare_mirror.py:269–313) checks hashes and fetches only missing file paths with rsync -az. Existing identical paths are not downloaded again. A fresh Mac already receives older versions via archives rather than every historical releases/ directory. But an already locally mirrored release's identical archive object can still be requested separately, because missing checks use paths rather than an existing release file with the same SHA. New manifest hashes/paths also prevent ordinary whole-file reuse across near-identical manifests.
- document_index (tushare_documents.py:1122–1350) has transaction-consistent dirty triggers. mappings/attempts/files use stable rowid ranges of 1000; append changes tail blocks, not every old reference. states use substr(id,1,2), 256 random hash buckets, so newly discovered unique documents dirties many state buckets. Re-observing an unchanged row only adds a reference, not a new document job. _index_original_files still scans/stat attachments/extracted names each build; count/group summaries scan SQLite; v2 is not zero full-directory/SQL-scan work.
- At assessed 316,831 document jobs (~1238 per state bucket), 1000 independent new hash IDs are expected to dirty ~250.9/256 buckets (98%). A pure-temp synthetic benchmark with 20,000 initial documents created 257 metadata files / 6,534,061 bytes; no-op created zero; adding 1000 created 253 files / 6,760,667 bytes and rebuilt252 buckets; one state update rebuilt1 bucket + compact index. Thus new unique discovery can effectively rewrite the whole current states snapshot even with v2. Total observed documents5.64GB cannot be attributed entirely to this: old v1 snapshots and all prior v2 files are intentionally retained; assessment does not classify their bytes by schema.

## Smallest ordered candidate

1. First, deduplicate immutable manifest aliases without changing logical manifests: archive copy can hardlink a fully verified source release manifest when same filesystem, fall back to current atomic copy on cross-device. Existing pairs can be verified bytes/SHA/size then atomically relink one alias via a temporary hardlink; no old path or byte disappears, no manifest or CURRENT changes. Only immutable release/archive files, never SQLite/WAL, active runtime files or attachments being written. Verify all parent/leaf paths against symlinks, reject existing mismatching bytes instead of overwriting, compare source stat before/after hashing/linking. Keep legacy probe IDs mapped to observed SHA with existing weaker authenticity statement. Potential same-host savings at most the ~2.89GiB archives total, not an audited guarantee. Ordinary hardlinks reduce physical blocks only; logical manifest bytes and fresh-Mac transfer remain unchanged. Hardlink alias corruption affects both paths, but existing SHA verification must still detect it.
2. Mirror can avoid duplicate transfer of archives/<sha>.json when a verified local releases/data-<sha>/manifest.json already exists: use the same safe immutable-link path before missing-files rsync, with copy fallback across filesystems. Do not let a damaged existing alias bypass verification or mask a corrupt local historical manifest. New-Mac first bootstrap still needs every retained distinct historical manifest. CURRENT-only closure, archived legacy mappings, predecessor comparison/self-archive projection remain unchanged.
3. Bounded metadata growth candidate: make state hash prefix explicitly versioned in the document index, use 3 hex chars (4096 buckets) for new snapshots, retain v1/v2 historical readers. This is a small writer trigger/cache migration plus reader prefix lookup change (router currently hardcodes ident[:2]); old shards remain untouched. At current rows, mean state bucket1238→77 (~16x smaller individual rewrite); 1000 new IDs expected to touch887/4096 (~21.7% of states instead of98%). More filenames, descriptors, disk-block overhead and initial one-time rebuilt index are real costs; very large batches still touch most buckets. Version the SQLite index metadata/triggers transactionally; old writers should continue to update via DB triggers; stale readers must reject unsupported format rather than silently lose states. Recommend measure 2-vs3 prefix synthetic and representative metadata before enabling; avoid arbitrary4-char/65k tiny files or a new generic storage framework.
4. Future separately scoped protocol change only if needed: content-addressed manifest inventory/dataset chunks or compressed immutable metadata transport. Compression benchmark of synthetic state metadata was ~5.8x smaller, but not a measured production ratio and rsync already compresses transport. Compression requires compatible hashes, bounded decompression, MIME/path/schema validators and historical reader support. Do not gzip/replace old manifests in place (release ID hashes their exact bytes). Do not omit old metadata from CURRENT.files unless a new recursively verified closure protocol supplies all retained versions; files needed by historical releases must still reach a new Mac.
